Why SLMs for decisions

Cost, latency, privacy and controllability — with the arithmetic that makes the case, and the cases where it does not.

On this page

The honest framing: an SLM is not a worse version of a large model. For a closed decision task it is a different tool with a different cost structure, and the economics usually dominate.

The arithmetic

Take a classification decision over 5M cases/month with ~600 input tokens each.

Weights in memoryn/a14 GB FP16360 MB

Throughput per corerate-limited~40 req/s per GPU~120 req/s per vCPU

Illustrative model, not a quote. Substitute your own token counts, instance pricing and utilisation before using this table in a business case. The ratios, not the absolute rupees, are the argument: two to three orders of magnitude between a frontier API call and a self-hosted SLM.

Five reasons that survive scrutiny

  1. Latency as a feature, not a cost. 10 ms versus 600 ms changes the product. Sub-50 ms enables inline decisions — flag a transaction while it authorises, route a support ticket before the customer finishes typing.
  2. Privacy by architecture. Data that never leaves the VPC cannot be leaked by a vendor. For health records, bank statements or employee data this is often the deciding constraint, not a bonus.
  3. Determinism and auditability. With temperature 0, a fixed prompt, a pinned tokenizer and a pinned quantisation, you can reproduce a decision bit-for-bit years later. Frontier APIs change under you; a versioned model artefact does not.
  4. Cost per decision near zero. Once the model is in memory, marginal cost is dominated by the request path, not the model. That makes high-volume, low-value decisions (tag every line item) economically possible.
  5. Constrained output spaces. A classification head cannot emit an unparseable string. With a decoder you get the same guarantee via grammar-constrained decoding or a strict schema validator — see edge cases.

Where an SLM is the wrong tool

SituationWhy SLMs struggleDo this instead
Open-ended generation quality mattersFluency and breadth are parameter-boundFrontier model, human in the loop
Decisions need recent world knowledgeWeights are frozen at training cutoffRetrieval + SLM, or a tool call
Long-horizon multi-step planningError compounding over hopsPlanner LLM + SLM executors (hybrid, ch. 07)
Zero labelled data, no teacher budgetCannot be tuned; prompting alone is brittle at this sizePrompt a large model first, distil later
Regulated high-stakes decisionsNo SLM alone is a defensible medical deviceSLM as a triage signal inside a governed pathway

The distillation economics

Getting a 360M model to 97% of a 70B teacher's agreement on a narrow task costs roughly:

teacher labelling    : 100k prompts × ~₹0.40      = ₹40,000   (one-off)
distillation train   : 3 epochs, 1× A10G, ~6 h     = ₹600
eval + calibration   : negligible
total                : ~₹41,000 one-off, then ~₹0.001/case forever

Break-even against an API at ₹0.40/case is ~100k cases. Above that volume, distillation pays for itself within the first month. Below it, use the API and revisit when volume grows — this is the same build-versus-buy calculus as any infrastructure decision.

Accuracy you should expect, by task type

From published distillation and small-model tuning results, in terms of agreement with a strong teacher on a narrow task — not absolute accuracy:

Task shapeTypical SLM agreement with teacherNotes
Topic / intent classification (≤ 20 classes)95–99%Easiest case; often matched by a linear model on embeddings
Sentiment / severity ordinal scoring90–96%Adjacent-class confusion dominates the error
Span extraction into a schema85–95% F1Degrades sharply with entity count per document
Short rationale + label80–92%Rationale quality is weaker than label quality
Arithmetic / multi-hop reasoning55–80%Where SLMs genuinely lose; add tools
Do not quote these as your result These ranges come from published work on specific datasets. Your number depends on label noise, class balance, and how much of the decision is genuinely ambiguous. Measure, then compare.

Decision checklist: SLM or API?

  • Volume × API price > build cost within 12 months?
  • Latency requirement below what an API round trip allows?
  • Data cannot leave your environment (contractual or regulatory)?
  • Decision is closed-set and stable over the next 6–12 months?
  • You can label or teacher-label ≥ 5k examples?
  • You can staff model maintenance (retraining, drift monitoring) for the life of the product?

Five or more yes: build the SLM. Fewer: wrap the API behind the same DecisionSpec interface so you can swap later without rewriting the product.
